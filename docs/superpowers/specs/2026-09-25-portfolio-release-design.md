## TL;DR

M10 turns the built tool into two things a stranger can look at: a public
demo and a case study draft. The demo runs the real app against a seeded
sample project, in a storage namespace separate from Nick's own projects, on
a Vercel preview deployment with `noindex` headers, no sign-in, and no
first-run tour. Analytics stay off. The sample project is built entirely
from S2's starter-kit props, so no licence questions ever come up. The case
study is a structure plus a citation list, not prose: the actual writing
happens later, in the SuperDesign `writing-case-study` skill, drawing only
from artifacts that already exist. Everything here stays unlisted until Nick
says go, per R9.

M10 needs M4 (Outputs) at minimum, so the demo can show a rendered clip and
storyboard export. VR is optional: the demo works with the flat editor alone,
and gains an "Enter VR" affordance only if M5 through M8 have shipped by the
time M10 starts.

## 1. Problem

The tool has been, up to M9, something only Nick can run: a dev server on
his own Mac, opening IndexedDB databases that hold his own projects. A
portfolio needs something a recruiter or a hiring manager can click without
installing anything, without an account, and without touching data Nick
cares about. It also needs a written account of the work, because a blank
demo answers "does it work" but not "what was hard, what got decided, and
why." Two failure modes to avoid: shipping a public URL that search engines
index before Nick has reviewed it, and writing a case study that invents
detail the interviewer can be asked to defend.

## 3. Alternatives considered

- **A separate, trimmed-down demo build.** Rejected: a second codebase drifts
  from the real one and doubles the maintenance surface for a tool that is
  still pre-1.0. One flag (`P2`) keeps the demo honest about what the app
  actually does.
- **A hosted backend seeding a shared demo database.** Rejected outright by
  D6. Every visitor gets their own local copy instead, which also means no
  visitor can see or break another visitor's edits.
- **Reusing the `sb3d` database with a special "demo" project id.** Rejected:
  a bug in the reset flow could touch Nick's real projects if he ever opens
  the demo build on his own machine. A separate database name makes that
  structurally impossible, not just policy.
- **A guided tour on first load.** Rejected per `P6`. The tool's target user
  in this milestone is someone evaluating Nick's work, not a new daily user;
  a tour adds build time for a persona that will not return.
- **Basic analytics (page views only, via a privacy-friendly host like
  Plausible).** Considered, rejected for M10 (`P7`). It is a real option for
  later, but it adds a vendor, a script, and a privacy stance to write down,
  none of which the demo needs to prove the tool works. Revisit if Nick wants
  visit counts before he shares the link widely.

## 4. Public demo

### 4.1 What M10 needs from earlier milestones

| Milestone | Needed for the demo? | Why |
|---|---|---|
| M1–M3 | Required | The app does not run without them: projects, props, takes, playback. |
| M4 Outputs | Required (the floor, `P1`) | The demo's most explainable feature is "here is a rendered clip and a storyboard PDF," which only M4 provides. Without it the demo is an editor with nothing to show for a shot. |
| M5–M8 VR | Optional | Each depends on a Quest headset to fully exercise, which a portfolio visitor on a laptop does not have. The flat app must stand on its own. |
| M9 AI video bridge | Optional, recommended | The package export (R7, R8) is a strong, self-contained thing to demo: "export a zip a video model can use" needs no external account to show, only to explain. |

M10 itself gates on M9 in the roadmap table, so in the fixed order every
earlier milestone including VR will exist by the time M10 starts. `P1` is
written defensively in case the order changes in review: it states the true
floor (M4) separately from the currently-planned actual state (M9 done, VR
done) so a future re-read of this spec does not assume VR when only the flat
app shipped.

### 4.2 Build-time flag

```ts
// src/app/demo.ts
export const DEMO_MODE: boolean = import.meta.env.VITE_DEMO_MODE === "1";
```

`VITE_DEMO_MODE` is a Vercel project environment variable, set to `1` only on
the demo project (`P8`), never on any client or personal project Nick
deploys from this same codebase in the future. Every place this spec asks
for demo-only behaviour reads `DEMO_MODE`; there is no second build config,
no second `index.html`, no second router.

Demo-only behaviour, gated on `DEMO_MODE`:

- The database name (`4.4`).
- The seed-on-first-load and "Reset to sample" affordances (`4.3`).
- The dismissible banner (`4.5`).
- The `noindex` response header and `robots.txt` content (`6.3`).
- Hiding the storage-status "changes are not being saved" nudge's link to
  `lastExportedAt` export reminders: the demo has nothing worth exporting
  for the visitor to lose (a visitor can still export by hand; the app does
  not nag them to).

Everything else runs unmodified: routes, stores, the viewport, undo,
autosave, the shot strip, VR if present. That is the point of `P2`.

### 4.3 The seeded sample project

**What it contains.** One project, two or three scenes, each with two or
three shots, enough to show the tool's range without asking a visitor to
build anything:

- A scene built from starter-kit props only (main spec S2: table, chair,
  sofa, bed, door, window, car, tree, crate, lamp, stairs, the reference
  figure), so the sample never depends on an imported `.glb` and never
  raises a licence question.
- At least one doll with a pose track (walk into frame, sit), to exercise
  `shot.tracks.poses`.
- At least one object position track (a car pulling into frame, a door
  swinging), to exercise `shot.tracks.objects`.
- At least one shot with two takes on the selected shot, one of them a
  `dollyIn` or `orbitLeft` move preset (camera-and-motion spec 4.6), so
  "New take" and `selectTake` have something to show.
- If M9 shipped by the time this is built: one shot with an AI package
  export ready to click, using the seed's own props so the guide clip
  renders from real geometry, not placeholders.
- If VR (M5+) shipped: no VR-only content is seeded, since a desktop visitor
  cannot enter VR to see it. The "Enter VR" button appears (per whatever M5
  ships) but the sample project needs no VR-specific data; every take it
  ships is playable and viewable flat.

**No licences, by construction.** Every mesh in the sample is either a
starter-kit primitive-built prop or a primitive object (box, cylinder,
sphere, plane, wall). Nothing is imported from an external asset pack, a
purchased model, or either predecessor repo's example content. This makes
`P3`'s generator provably licence-clean: it has nothing to attribute because
it draws from nothing external.

**Generation.** `scripts/seed-sample-project.ts` is a Node script, not a
hand-maintained JSON fixture:

```ts
// scripts/seed-sample-project.ts
// Runs against src/domain and src/state's pure recipes directly (no browser,
// no IndexedDB): createProject, addScene, addStageObject (kit props and
// primitives), createShot, addTake, applyMovePreset, setObjectKey,
// setPoseKey. Writes the resulting Project as JSON.
export function buildSampleProject(): Project;
export function writeSampleProjectFile(outPath: string): Promise<void>;
```

Running the same domain and state functions the app itself calls means the
sample project can never drift out of schema: if `Project` gains a required
field, the script fails to typecheck before a broken sample ever ships. The
output is written to `src/app/demo/sample-project.json` and checked into
git, reviewed in PR diffs like any other generated fixture (comparable to
`db.ts`'s schema, above).

**Versioning.** The file's own `schemaVersion` field is the version; there is
no separate version number to keep in sync. When a schema migration ships
(main spec, Storage: "read `schemaVersion`, run migrations"), the seed
script is re-run against the new `createProject`, producing a fixture already
at the new version, and the demo's seed-on-first-load path never needs a
migration step at runtime. If the checked-in fixture and the current
`schemaVersion` disagree (someone forgot to re-run the script after a schema
change), `pnpm test` fails on a dedicated unit test that loads the fixture
through the same Zod validation import does (main spec Storage), catching
the drift before it reaches a deploy.

**Seed-on-first-load and reset.** On `DEMO_MODE`, the projects list route
(main spec Navigation, `/`) checks whether the `sb3d-demo` database has any
project. If not, it writes a fresh copy of `sample-project.json` with a new
project id (the same "fresh id, ids inside the document unchanged" rule
import already follows) and blobs for the seed's own thumbnails, generated
the same way any project's thumbnails are (main spec Navigation, shot strip).
"Reset to sample" (`4.5`) re-runs the identical write, after confirming with
the visitor, discarding whatever they changed. Reset never touches
`localStorage` beyond the banner-dismissed flag (`4.5`); the project data
itself lives entirely in the `sb3d-demo` IndexedDB database, so reset is a
`deleteDB` on that store plus the same seed write, not a page-by-page clear.

### 4.4 Demo storage namespace

```ts
// src/storage/db.ts, extended
export const DB_NAME = DEMO_MODE ? "sb3d-demo" : "sb3d";
```

This is the one line that makes `P4` true. `openDb()` and every caller in
`src/storage` are otherwise unchanged: they already only ever reference the
`DB_NAME` export, never a literal string (confirmed by reading
`src/storage/db.ts` on `origin/feat/s0-s1-walking-skeleton`). A visitor who
also happens to run the real app in the same browser profile (unlikely, but
not impossible if Nick opens the demo URL on his own Mac to check it) gets
two separate IndexedDB databases with no shared keys, no shared blobs, and no
code path that can read one while `DEMO_MODE` selects the other. The Web
Lock name (main spec, Storage, "two tabs") is derived from the project id
inside whichever database is open, so demo and real-app locks never collide
either.

No new IndexedDB schema. `sb3d-demo` uses the exact same object stores,
indexes and version as `sb3d` (`Sb3dSchema`, unchanged); only the database
name differs.

### 4.5 No sign-in, no tour, the reset banner

- **No sign-in.** Nothing in the app today or in any owned milestone spec
  creates an account, a session, or a login form. `P5` records this as a
  standing decision rather than leaving it implicit, since a portfolio demo
  is exactly the kind of build where "let's add a quick login so we can see
  who's trying it" gets proposed later. The answer stays no.
- **No tour.** No spotlighted first-run walkthrough, no tooltip sequence
  timed to page load, no modal blocking the canvas on first paint (`P6`).
- **The one banner.** A dismissible bar above the shot strip, shown on
  `DEMO_MODE` only:

  > This is a public demo of scene-builder-3d, an in-progress previs tool.
  > Changes save to your browser only. [Reset to sample]

  Dismissing it sets `localStorage["sb3d-demo-banner-dismissed"] = "1"` (the
  one and only piece of demo `localStorage`, read with the same try/catch
  discipline as any other browser-storage read, main spec conventions), and
  it does not reappear for that browser. "Reset to sample" opens a small
  confirm ("Discard your changes and reload the sample project?") before
  calling the reset path in `4.3`. The banner and reset control live in
  `src/app/demo/DemoBanner.tsx`, mounted once in the stage layout alongside
  the shot strip, so it survives scene-to-shot navigation the same way the
  canvas does (main spec, Stage layout).

### 4.6 Performance budget for a first visit

A visitor with no context and no patience gets one chance. Budget, measured
on the deployed Vercel preview, throttled to a fast 4G / mid-tier laptop
profile in Chrome DevTools (the standard Lighthouse "Mobile" throttling
preset, confirmed at milestone start against whatever Lighthouse version CI
uses. That is a tool-version detail, not a fact about Nick, so it is not asserted
here without checking):

| Stage | Budget | Measured how |
|---|---|---|
| First contentful paint (the projects list shell) | Under 2.0 s | Lighthouse, CI run on the preview URL |
| Time to the seeded project's board page, first visit (includes the seed write) | Under 4.0 s | Manual stopwatch plus a Playwright timing assertion in the smoke test (`7`) |
| Time to the seeded project's board page, repeat visit (seed already written) | Under 1.5 s | Same |
| JS bundle, demo route's initial chunk | Under 350 KB gzipped | `vite build` output, checked in CI (a size-limit style check, not a new tool: reuses whatever bundle analysis M1 to M4 already run, or a plain `du` on `dist/` if none exists yet) |
| WebGL first frame after the board page mounts the canvas | Under 500 ms | Manual, Chrome and Safari (finishing-a-task rule) |

These are demo-specific budgets, additive to whatever performance bar the
earlier milestones already hold the app to; M10 does not relax anything M1–M9
established. A budget miss is not a hard blocker for merging the build
slices below, but every miss is logged in the launch checklist (`6.4`) and
either fixed or explicitly accepted before Nick says go to list the demo.

### 4.7 Analytics

None (`P7`). No script tag from any analytics vendor, no custom event
recording, no `fetch` to any endpoint the app does not already talk to
(there is none: D6). If Nick later wants visit counts, that is a new,
separate decision. It touches privacy disclosure and possibly a
`robots.txt` or cookie-consent question this spec does not answer, and gets
its own line in a future spec rather than being smuggled into M10's launch
checklist.

## 5. Deployment

### 5.1 Vercel project and target

A dedicated Vercel project for the demo, distinct from any project Nick uses
for client work, named for this repo (`scene-builder-3d` or
`scene-builder-3d-demo`, confirmed at milestone start against whatever is
free in his Vercel team, a naming detail only he can settle and not asserted
here). Every deploy from this milestone's branch runs:

```
vercel deploy --target preview
```

never a bare `vercel deploy` and never `--prod`, until Nick explicitly says
go (`P8`, and the standing rule in memory:
`vercel-first-deploy-goes-to-production.md`, which records that a bare
`vercel deploy` on a *new* project targets production with a public alias,
the exact trap `--target preview` exists to avoid here). Preview deploys get
Vercel's own auto-generated URL; no custom domain is attached until listing.

### 5.2 `noindex` while unlisted

Two layers, per `P9`:

1. **Response header**, set in `vercel.json` for every route on the demo
   project while `VITE_DEMO_MODE=1`:

   ```json
   {
     "headers": [
       { "source": "/(.*)", "headers": [
         { "key": "X-Robots-Tag", "value": "noindex, nofollow" }
       ] }
     ]
   }
   ```

2. **`robots.txt`**, served from `public/robots.txt`, generated per build
   (a tiny build-time script, `scripts/write-robots.ts`) so it flips
   automatically when `DEMO_MODE` and the eventual "listed" flag (`5.3`)
   change:

   ```
   User-agent: *
   Disallow: /
   ```

Both layers are removed together, in the same change, when Nick says go.
Never one before the other, since a `robots.txt` allow with a lingering
`noindex` header (or the reverse) just confuses crawlers about which one to
trust.

### 5.3 Unlisted to listed

"Unlisted" means: deployed, reachable by anyone with the exact URL, not
linked from vyhouski.com, not linked from any works index inside this app
(there is none: the demo is a single project, not a portfolio site of its
own), and carrying the `noindex` header and disallow rules above. "Listed"
means Nick has added the link to vyhouski.com and/or a works index, and the
`noindex` header and `robots.txt` disallow are removed in the same PR that
does so. There is no intermediate state; the switch is binary and happens in
one reviewed change, per the portfolio-work-defaults-to-unlisted standing
rule.

## 6. Launch checklist

Run in full before any "unlisted to listed" switch (`5.3`), and after every
deploy that changes demo-affecting code, as a lighter pass:

### 6.1 Full checklist (before going listed)

1. Deployed preview URL loads with a cold cache in both Chrome and Safari,
   desktop, no console errors (finishing-a-task rule: a green build is not a
   working page).
2. `sb3d-demo` seeds on first visit; `sb3d` (a real project, if one happens
   to exist in the same browser profile from local dev) is untouched,
   checked by hand with DevTools' Application tab, listing both databases.
3. "Reset to sample" round-trips: edit an object, reset, confirm the edit is
   gone and the sample is back exactly as seeded.
4. Every seeded shot plays back, in both browsers: `cameraAt` samples
   correctly, tracks animate, the timeline scrubs.
5. If M4 shipped: the seeded shot's clip render and storyboard PDF/zip
   export both complete and the output opens.
6. If M9 shipped: the AI package export completes and the zip's contents
   match the outputs-design spec's format.
7. If VR shipped: "Enter VR" is present and, on a Quest browser pointed at
   the deployed URL over HTTPS, the session starts (this one check needs the
   headset; every other row is desktop-only).
8. Performance budget (`4.6`) measured on the actual deployed URL, not
   localhost (Browser-pane rule: re-check the deployed URL before claiming a
   fix landed).
9. `curl -I` on the deployed URL shows `X-Robots-Tag: noindex, nofollow`;
   `/robots.txt` on the deployed URL shows `Disallow: /`.
10. No analytics script, no third-party request, appears in the Network tab
    on a fresh load (confirms `P7` by observation, not just by absence of
    code).
11. The case study draft (`7`) exists and links to this exact preview URL.

### 6.2 Light pass (routine redeploys)

Steps 1, 4 and 9 only, in Chrome. Full checklist re-runs before the listed
switch regardless of how recently a light pass ran.

### 6.3 Recording the result

The checklist run and its pass/fail per row is recorded the same way M1's
closing checks were: as a short note in the PR description for the change
that triggers a full run, not as a separate tracked document. A failed row
blocks the "unlisted to listed" PR; it does not block ordinary preview
redeploys, which only need the light pass.

## 8. Error handling

| Failure | Behaviour |
|---|---|
| `sb3d-demo` fails to open (IndexedDB unavailable, quota exceeded) | The main spec's own fallback applies unchanged: the app runs in memory behind the persistent "changes are not being saved" banner. The demo banner (`4.5`) still shows underneath it; the two are not mutually exclusive. |
| Seed write fails partway (quota exceeded while writing seed blobs) | The projects list detects an incomplete seed (no project row, or a project row with no scenes) on next load and retries the full seed write from scratch rather than resuming a partial one. Never shown as a broken empty project. |
| "Reset to sample" fails mid-`deleteDB` or mid-reseed | The confirm dialog's action shows a retry state; the visitor's prior (possibly edited) project is not assumed lost until the reset actually completes, so a failed reset leaves the old data in place rather than an empty database. |
| A visitor's browser blocks IndexedDB entirely (strict private-browsing mode, disabled storage) | Same as the main spec's own IndexedDB-unavailable path: in-memory only, banner shown. The demo still functions for the length of the session; nothing is lost until the tab closes, which is disclosed by the existing banner copy. |
| The seed fixture (`sample-project.json`) fails its own schema check at build time (P3, the drift-catching unit test) | The build fails in CI. No demo deploy ships with a fixture that cannot load. |
| A demo visitor's browser is old enough to lack WebXR (`P1`, VR optional) | "Enter VR" is not rendered at all. Same feature-detection the real app already needs for M5, not a demo-specific check. |
| `robots.txt` or the `X-Robots-Tag` header fails to apply on a given deploy (a Vercel config regression) | Caught by launch-checklist row 9 (`6.1`) before the "unlisted to listed" switch; a routine preview redeploy without that check is still `noindex`-eligible by default until the switch, so the exposure window is a misconfigured preview, never a misconfigured *listed* page. |
| The demo video recording shows a bug the checklist missed | Recording stops; the bug is fixed and the full checklist (`6.1`) re-runs before recording resumes. A video is never published showing a state the checklist would have failed. |

  `"1"`, so a typo never silently turns the demo on).
- `db.test.ts` addition: `DB_NAME` resolves to `"sb3d-demo"` under

**Storage, against `fake-indexeddb`.** Seeding writes into `sb3d-demo` and
never touches a `sb3d` database present in the same fake environment; reset

## 11. Build slices

Each slice ships behind `VITE_DEMO_MODE`, so none of it affects the real app
until the flag is set on the demo Vercel project.

### Slice A: demo flag and storage namespace

1. `DEMO_MODE` reads the env var; `DB_NAME` switches on it (`4.2`, `4.4`).
2. **Done when:** a local build with `VITE_DEMO_MODE=1` opens `sb3d-demo` in
   DevTools' Application tab, and a build without it opens `sb3d`, confirmed
   in the same browser profile without one affecting the other.
3. **States covered:** flag on, flag off, both in the same profile.

### Slice B: seed generator and seed-on-first-load

1. `scripts/seed-sample-project.ts` builds and writes
   `sample-project.json` (`4.3`). The projects list seeds `sb3d-demo` on
   first load when empty.
2. **Done when:** a fresh `sb3d-demo` database, opened in the demo build,
   shows the seeded project with every scene, shot, take and track listed in
   `4.3` present and playable; a second load does not reseed (no duplicate
   project).
3. **States covered:** empty database (seeds), already-seeded database
   (no-op), seed write interrupted mid-way (error handling row 2).

### Slice C: reset, banner, no-tour

1. `DemoBanner.tsx` mounted in the stage layout; "Reset to sample" wired to
   the reset path (`4.3`, `4.5`).
2. **Done when:** the banner shows once, dismiss persists across reload,
   reset discards an edit and restores the seed exactly, and no tour or
   tooltip sequence appears anywhere in the demo build.
3. **States covered:** banner shown, dismissed, reset confirmed, reset
   cancelled.

### Slice D: deployment, headers, robots

1. Vercel project created, `--target preview` deploys, `vercel.json`
   `X-Robots-Tag` header, generated `robots.txt` (`5`).
2. **Done when:** the deployed preview URL responds with the `noindex`
   header and disallow rules, confirmed with `curl -I` and a fetch of
   `/robots.txt` against the live URL, not localhost.
3. **States covered:** unlisted (this slice's end state); the listed switch
   itself is not built here, only the toggle point described in `5.3`.

### Slice E: launch checklist run and case study draft

1. Run the full checklist (`6.1`) end to end. Write the case study's
   structure and source table (`7.2`, `7.3`) into a draft file on
   vyhouski.com's repo or a shared doc, whichever that site's own workflow
   uses (confirmed at milestone start). Record the short video (`7.4`) after
   the checklist passes.
2. **Done when:** every checklist row passes or has a recorded, accepted
   exception; the case-study structure document exists with every row of
   `7.3` linked to a real URL; the video file exists and plays.
3. **States covered:** checklist pass, checklist fail-and-fix (at least one
   row is expected to fail on the first run, per the finishing-a-task rule
   that a green build proves nothing by itself).
